# 工作区与上下文连续性 v5.0.0

> 当前软件包：**川序社区版**；支持底座：**oracle, pg, yashandb**；版本类别：**Community**；许可：**Apache-2.0**。文中其他底座及企业专属能力用于说明差异，不表示此包包含或支持这些能力。

[English](workspace.md)

## 数据库实体与授权

工作区、工作区上下文、会话、分支和关联任务均复用现有数据库实体。稳定标识、
来源关系和历史由数据库保存；JSON 承载有界正文，不承载另一套权限或任务引擎。
本产品支持 **oracle, pg, yashandb**。

通过已认证的 Dashboard/Gateway 操作访问资源，并检查当前权限。
`scripts/lib/workspace_api.py` 中的 Python 函数是内部基础操作，不能作为授权边界。
原生 Agent 登录仍受所选数据库的独立策略约束。工作区的 `SHARED` 或
`ISOLATED` 元数据不会授予知识、记忆、频道、模型或其他主体的数据权限。

PostgreSQL 使用原生 JSONB 和结构中定义的数据库生成数值标识；Oracle 和
YashanDB 使用各自原生结构与适配器。Oracle 的 JSON 关系二元性视图属于该适配器
的投影，不能当成三库通用写入接口，也不能把 Oracle JSON/SQL 语法直接复制到其他底座。

## 工作区生命周期

| 状态 | 含义 | 预期后续状态 |
|---|---|---|
| `ACTIVE` | 当前工作上下文 | `PAUSED`、`COMPLETED`、`ABANDONED` |
| `PAUSED` | 暂停工作 | `ACTIVE`、`COMPLETED`、`ABANDONED` |
| `COMPLETED` | 工作已完成 | 保留结果与历史 |
| `ABANDONED` | 工作已放弃 | 保留原因与历史 |

`WORKSPACES` 保存所有者、名称、类型、隔离元数据、当前 Agent 和会话、摘要及时间。
`WORKSPACE_TASKS` 关联任务计划，不复制其执行状态。Dashboard 的授权清单入口是
`GET /api/workspaces`；`view=summary` 返回其有界摘要。读取接口存在不等于支持写入。

## 上下文类型与正文

`WORKSPACE_CONTEXT` 将父上下文、工作区、Agent、会话及分支关系与
`CONTEXT_DATA` 正文分开保存。

| 类型 | 正文用途 |
|---|---|
| `SNAPSHOT` | 某个已记录时刻的工作状态 |
| `CHECKPOINT` | 中间进度和待办事项 |
| `HANDOFF` | 交接原因、当前状态和接收方说明 |
| `SUMMARY` | 有界的会话结果摘要 |
| `RECOVERY` | 恢复点、中断情况和继续工作的说明 |

建议的正文结构如下：

```json
{
  "_version": 1,
  "summary": "Validation is incomplete",
  "pending_actions": ["Verify the remaining task"],
  "observed_at": "2026-10-17T00:00:00Z"
}
```

这只是结构示例，不是执行证据或授权。正文应限制大小、标明结构版本，并使用
ISO-8601 时间。不得写入凭据。服务虽会清理类似秘密的字段，调用方仍须避免把
秘密写进任意文本段落。

## 交接与分支关系

旧的 `create_handoff_session()` 函数创建 HANDOFF 分支，将新 `AGENT_SESSION`
关联到前一会话，保存上下文，再更新工作区当前 Agent 和会话。几个独立基础操作
不能证明治理交接原子完成，也不能证明接收方已接受。新的工作应使用
[连续性操作](continuity-operations_zh.md)中的版本化工作契约、交接邀约/确认和上下文组装流程。

这些流程保存职责、策略修订、精确来源快照、摘要、当前授权，以及不可变的审核和
发布事实。并行容量需明确设置且受到限制；协调者所有权与接收方权限分开。
文字指令或分支名称不能转移所有权，接收方仍须具备读取每项来源的当前权限。

DB4A2A 传递上下文引用和精确快照事实，避免重复复制大段提示词。授权的子分支
操作锁定并检查派发和上下文，在同一事务中提交分支、关联与审计；重试时来源发生
变化会被拒绝。详见 [DB4A2A](db4a2a_zh.md)。

## 恢复与执行

`recover_workspace()` 组装可用的工作区元数据、有界的上下文和会话历史、关联的
活跃任务及适用的范围内实体。它不会继续模型计算、重跑外部操作、提升数据库备库，
也不能证明此前副作用失败。继续工作前须检查原任务、尝试、租约、检查点和来源修订。

使用 `RECOVERY` 上下文记录所选恢复点及理由。过期 Worker 的隔离令牌不能提交；
结果不明的外部发送必须核对，不能盲目重发。原 Gateway 凭据撤销后，不能用新凭据
替代旧凭据继续原请求。数据库备份、复制及 RPO/RTO 由运维方负责。

## 操作与验证

1. 选择有权访问的工作区，检查所有者、状态和当前会话。
2. 交接或 DB4A2A 派发前，查看精确来源上下文和分支。
3. 使用带预期修订和幂等键的治理操作。
4. 读取结果记录和审计；排队成功不等于执行完成。
5. 成员、来源或凭据撤销后重新检查权限。
6. 在明确分类的临时目标上验证重启和未知结果处理。
