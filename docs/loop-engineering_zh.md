# 循环工程 v5.0.1

> 当前软件包：**川序社区版**；支持底座：**oracle, pg, yashandb**；版本类别：**Community**；许可：**Apache-2.0**。文中其他底座及企业专属能力用于说明差异，不表示此包包含或支持这些能力。

[English](loop-engineering.md)

## 目的与实体

Loop 记录目标、有界迭代、观测、评估和停止条件。本文说明产品自身实现，不将工程方法发展顺序或未经核实的人物归属作为事实。

定义保存在 `ENTITIES` 中，类型为 `LOOP_DEFINITION`，由 `LOOP_META` 扩展；运行、迭代和钩子分别保存为数据库记录。Harness 可提供执行蓝图。Loop 关联现有上下文分支、工作区上下文和任务计划/步骤，无需另建无类型编排存储。所选数据库适配器保存这些事实，厂商专用 SQL 留在适配层。

## 操作流程

1. 创建定义，明确目标、负责人或 Agent、评估配置，以及迭代次数、Token 和时长上限。
2. 启动运行，通过授权服务记录每轮意图、操作、观测、调整与实测消耗。
3. 评估已提交的迭代，检查结果和证据，再决定是否继续。
4. 显式暂停、恢复、停止、失败或完成运行；进程重启后重新检查当前状态和停止条件。
5. 保留运行、迭代历史及关联任务结果。

使用 Dashboard `/app/loops` 或 [API 参考](api-reference_zh.md)中的已认证循环接口。`lib.loop_api` 的 Python 函数是服务实现接口，不代表普通 Agent 可使用 Schema Owner 身份调用。Loop 记录不会自行执行任意代码；工具、模型、Skill 和外部效果继续遵守原有授权与运行控制。

## 评估与钩子

支持 `TEST`、`DIFF`、`LLM_JUDGE`、`MANUAL`、`SPEC_VALIDATION` 和 `AGGREGATE`。结果应保留输入观测与评估配置。模型评审须使用已批准、可用的模型；输出是决策证据，不能自行修改权限或发布知识。测试和差异评估消费有界结构化观测。

生命周期钩子包括 `PRE_RUN`、`POST_ITERATION`、`ON_STOP`、`ON_FAIL`、`ON_TIMEOUT` 和 `ON_START`。钩子类型与处理器以当前实现为准；登记钩子不代表远端操作已发生，应检查服务结果和审计。

## 复用已有能力

| 关联对象 | 行为与边界 |
|---|---|
| 规格 | `create_loop_from_spec` 从验收条件推导目标，使用前检查推导输入 |
| 任务步骤 | `bind_loop_to_step` 保存 `TASK_LOOP_BINDING`，通过既有生命周期更新关联步骤 |
| 分支 | 提供隔离上下文，合并仍需单独治理决策 |
| Skill | 取得 Skill 时可按配置创建验证循环 |
| 协作循环 | 子运行聚合观测；历史协作组关联不授予安全域权限 |

协作嵌套最多两层。步骤完成类型包括 `MANUAL`、`LOOP` 和 `SPEC`，等待中的步骤可进入 `WAITING_LOOP`。完成回调保留原始关联，不能从旧成功标记推断不存在的工作已完成。

## 恢复与证据

数据库保存当前状态和迭代历史，允许 Agent 重启后继续授权检查。这不保证任意外部操作可以安全重试，也不保证所有模型对话可以恢复。不确定效果须记录并核对，不能直接重发。重建上下文时遵守当前权限和来源撤销。

带租约的图执行见[图工程](graph-engineering_zh.md)，分支和上下文生命周期见[工作区](workspace_zh.md)，进程与数据库恢复边界见[恢复指南](recovery_zh.md)。不能用独立 Loop 调度器替代这些持久化服务，也不能通过进程重启测试宣称数据库集群高可用。
